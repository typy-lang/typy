# What's new in TyPy 0.7

TyPy 0.7.0 was released on 2026-11-18. This page summarises what it
changes for you as you write programs; the
[changelog](changelog.md#070-2026-11-18) lists every change, with the
requirement and the decision record of each.

## Summary

- TyPy runs on macOS 11 or later on Apple silicon, and builds programs
  and libraries for macOS there.
- `ctypes.CDLL(None)` calls the C library and the maths library every
  program links, so a program that needs only those runs on Linux and
  macOS alike.
- The compiler links an LLVM that TyPy builds from LLVM's signed sources,
  and needs no `libffi`, `zlib` or `zstd` on Linux.

## macOS on Apple silicon

Each release has a third archive, `typy-0.7.0-aarch64-apple-darwin.tar.gz`,
for Macs with Apple silicon. The programs and libraries it builds run on
every Apple silicon Mac from macOS 11 (CLI-15). A Mac builds for macOS
alone, and a Linux machine does not build for macOS, since linking for
macOS needs Apple's tools; `--target` with another system's triple is a
usage error that lists the host's targets (CLI-08).

A program behaves as under CPython on macOS: `sys.platform` is `"darwin"`
(LIB-22), an `OSError` takes macOS's error numbers and the texts its
`strerror` gives (EXC-19), and a C function reads the values CPython's
`ctypes` passes it under Apple's arm64 convention (FFI-13). TyPy's test
suite runs every conformance test natively on macOS and compares it with
CPython for macOS (NFR-17).

A debug build writes `NAME.dSYM` beside the program, which `lldb` reads.
A shared library is named as macOS names libraries, `libNAME.5.dylib` with
the link `libNAME.dylib` for release 5.1, and a static library
`libNAME.a` (CLI-16).

The archive is signed ad hoc and not notarized, so an archive a browser
downloads needs its quarantine cleared once;
[Using TyPy on macOS](../using/macos.md) shows each step.

## Portable C calls

`ctypes.CDLL(None)` and `ctypes.cdll.LoadLibrary(None)` declare the C
library and the C maths library, which every program links, with nothing
more to link (FFI-14):

<!-- typy-expect: accepted -->
```python
import ctypes

own = ctypes.CDLL(None)
own.labs.argtypes = [ctypes.c_long]
own.labs.restype = ctypes.c_long
own.cbrt.argtypes = [ctypes.c_double]
own.cbrt.restype = ctypes.c_double
print(own.labs(-12), own.cbrt(27.0))
```

The same program runs under CPython, where `CDLL(None)` finds the
functions the process has loaded. A library of one system, such as
`libm.so.6` on Linux or `libm.dylib` on macOS, still works on that system
alone; see [Calling C through ctypes](../extending/c-interop.md#calling-c-through-ctypes).

## TyPy's own LLVM

The compiler links LLVM 23.1.6, which TyPy builds from LLVM's signed
sources for each host it runs on, so every build of one commit links the
same LLVM bytes, and a release rebuilt from its tag matches the published
archive. The Linux compiler now needs glibc 2.39 or later and `libstdc++`
alone; `libffi`, `zlib` and `zstd` no longer have to be installed.

## Other changes

- A function a library exports takes and returns a `bool` as the target's
  C compiler passes `_Bool`, so a C caller on AArch64 Linux, which does not
  extend it, passes it correctly.
- `typy check --target` checks for the target's system, as `sys.platform`
  shows.
